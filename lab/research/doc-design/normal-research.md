## 1–2. The sites people rate highest, and how they're structured

Two long-running Hacker News threads are the best available proxy for "what developers actually rate highest," because they're unprompted, cumulative over years, and self-correcting (people push back on picks they disagree with). Pulling from both threads directly:

**Django** (web framework) is the single most repeated answer across both threads, and for a specific, named reason: a developer explained the documentation's "layering" — from beginner tutorial through high-level subsystem overviews, through detailed subsystem usage, through API-level docs, through to the source code — all linked together, at every layer full of notes and caveats appropriate to that layer. That's the opposite of strict content-type separation: it's a single spine that changes altitude as you read.

**Stripe** (payments API) is the other repeat name, but its reputation source is more traceable than most: it comes up unprompted in the same thread and forum discussions years apart, was the subject of dedicated conference talks at APIdays (Stripe's own DevRel lead presenting "Building for Builders" in 2017, and an outside talk on developer docs referencing Stripe in 2016), and gets cited specifically for the completeness and browsability of its API reference — each operation described in plain language alongside the exact arguments and a copy-pasteable request/response pair. Worth noting: it's not unanimous — one HN reply says newer integration work with Stripe found the docs "lacking in significant details" and shallow enough to need support follow-up, so treat "best" as "most frequently cited," not "flawless."

**MDN** (web platform reference) is called "spectacular" and repeated as exhaustive; its reputation is tied to a specific, documented event — a deliberate content refactor of the JS reference that predates most of the current praise.

**PHP's manual** gets an unusually specific defense: individual pages per function, explicit input/return types, a search that prioritizes reference over blog chatter, and — historically — user-submitted notes at the bottom of each page that captured gotchas, though those notes degraded over time as they weren't revalidated.

**PostgreSQL, SQLite, Redis, scikit-learn, cppreference, Elixir/HexDocs, Rust's docs.rs** all recur. The reasons given cluster around three things: SQLite's docs use flow-diagram syntax charts to make grammar precise; scikit-learn's docs pair the API reference with the underlying math/theory so "you can literally learn Machine Learning just by reading the docs"; and docs.rs and HexDocs are praised because doc generation is built into the language toolchain itself, which forces a consistent format across the entire ecosystem rather than depending on each maintainer's individual effort.

**GitHub Actions**, **Terraform**, and **HAProxy** are the config-heavy outliers in these threads (relevant to you) — I cover their structure in section 5.

### Structure, in the terms you asked about

Across the highest-rated sites, four patterns hold with unusual consistency:

- **Sidebar + landing/index page, not one or the other.** Every site above uses both: a persistent sidebar for people who arrive mid-task from search, and a landing page that routes first-time readers. None relies on sidebar alone.
- **Most traffic lands mid-document from search, not at page one.** This is inferred from the sites' own design choices (version switchers, "on this page" mini-TOCs, self-contained pages that re-state prerequisites) rather than from a single cited study, but it's consistent enough across Django, MDN, and PostgreSQL that I'd call it a working consensus rather than a hard finding.
- **Reference is deep and separate; explanation is threaded through or linked from it, not walled off.** Django's explicit design goal was that every layer — tutorial, subsystem overview, subsystem usage, API reference, source — exists and links to the others, which is a rejection of hard separation, not an embrace of it.
- **Page length varies by genre, not by site quality.** Reference pages (PHP, MDN, cppreference) are short and atomic — one function per page. Guide-style pages (Django subsystem docs, scikit-learn) run long, sometimes textbook-length, because they're teaching a concept, not looking up a signature.

I don't have a rigorously sourced answer on "how deep the tree goes" beyond direct observation — no survey measures this across sites — so I'll flag that as thin evidence rather than invent a number.

## 3. Does Diátaxis survive contact?

This is the part where the evidence gets genuinely interesting, and where you should be skeptical of confident claims in either direction.

**The success stories are real but self-selected.** Diátaxis's own site cites Gatsby and Cloudflare as adopters who found the four-quadrant model clarified where new content should go. These are testimonials collected by the framework's creator for the framework's own site — useful, but not independent evidence.

**The most informative case is Python's, because it's public, multi-year, and unresolved.** In 2022, Python's documentation working group reached "rough consensus" in a docs meeting to adopt Diátaxis. The same week, a maintainer opened a tracking issue — "Diátaxis: Where are we?" — noting "general consensus that diátaxis is a great theoretical model for structuring documentation. However, using it — restructuring Python's docs — is a monumental task that needs some planning upfront." The proposed first step was just to chart where existing docs already fell on the Diátaxis grid before touching anything. That issue is **still open**, years later, with no restructuring completed. That's not a rejection — nobody published a "we tried it and it failed" postmortem — but it is a stall: theoretical buy-in without operational follow-through, at one of the most-resourced documentation efforts in open source. A parallel 2023 thread ("Diátaxis and Python documentation") relitigated the same territory, which tells you the 2022 consensus didn't actually resolve anything.

**Where teams did push back, the objection was almost always the same: boundary-crossing costs more to enforce than it saves.** One Python core contributor pointed out that inline examples routinely have to break the "pure" content type to include enough context to make sense — and once inserted, readers have to scroll past that context every time thereafter, even after they've internalized it once. Separately, on evaluating Diátaxis for a new project, a developer wrote bluntly: "I looked for 20 mins, read about 2 of the pages in full and skimmed over another 4... and I still have no idea what it is... the docs were IMO also filled with way too much fluff, as well as unnecessarily many links to 'look who uses this.'" That team didn't adopt it.

**Even sympathetic technical-writing analysis names the specific cost as "content drift" plus "manual effort."** A framework of quadrants sounds solid in theory, but "its purity is difficult to preserve through manual effort alone, especially in fast-moving development environments with many contributors" — how-to guides accrete explanation, reference gets cluttered with steps — and auditing an existing large doc set to reclassify everything into four types "is a massive project" that "often requires dedicated resources that many teams can't spare, causing adoption to stall." That's precisely what happened to Python.

**Nobody I could find has published a "we adopted it, then reverted" postmortem.** That's a real gap, and I'll say so plainly rather than paper over it: the visible failure mode isn't reversal, it's **stall** — teams agree the theory is sound, start the audit, and never finish restructuring, while individual new pages continue to be written in whatever the previous ad hoc pattern was.

**The strongest counter-evidence that hard separation is optional comes from what highly-rated sites actually do.** GitHub's public documentation style guide doesn't use Diátaxis's four types at all — it publishes seven content types (conceptual, referential, procedural, troubleshooting, release note, quickstart, tutorial), a deliberately expanded taxonomy that splits "how-to" into three practical variants and keeps quickstart and tutorial distinct. This is a large, well-regarded team that looked at the same four-way split and decided it needed more categories, not that four was wrong.

**Verdict, stated as evidence allows:** Diátaxis is best understood as a *diagnostic vocabulary* — a compass for noticing when a page is doing two jobs badly — rather than a mandatory site architecture. Every team that publicly engaged with it seriously ended up either (a) partially adopting the vocabulary while keeping their existing structure, (b) expanding it into more categories for their domain, or (c) stalling on the full restructuring. Nobody in the public record fully implemented it and then found it net-negative, but nobody has actually finished implementing it at scale either, except smaller teams working from a blank slate.

## 4. What makes documentation rated badly

This is the best-evidenced section, because it's been measured, repeatedly, by different methods.

**Measured, not opinion:**

- GitHub's 2017 Open Source Survey (5,500 randomly sampled respondents from 3,800+ repositories, plus 500 from outside the GitHub ecosystem) found incomplete or outdated documentation is a pervasive problem observed by 93% of respondents, yet 60% of contributors say they rarely or never contribute to documentation themselves. In the same survey, incomplete or confusing documentation was the single most annoying issue people encountered with open source projects, ahead of unresponsiveness, dismissiveness, or conflict.
- A 2021 academic study (Khan et al., SANER) built a benchmark of 1,000 real Javadoc units and found 778 of them (78%) exhibited at least one of five documented "smells": bloated (too long), tangled (mixing multiple things), fragmented (scattered across too many pages), excess structural information (irrelevant type/inheritance detail), and "lazy" (adds nothing beyond what the method signature already says). They then surveyed 21 professional developers, and 95.2% said these smells actively hurt their productivity. The catalog traces back to an earlier, larger survey of 323 IBM developers by Uddin and Robillard (2015), so this isn't a one-off finding — it's been replicated across two independent developer populations, roughly a decade apart.
- A separate survey specifically on class-level documentation found five distinct information needs where more than 90% of respondents reported non-zero annoyance, and even the single least-annoying need still bothered 50% of respondents.

**Your specific failure modes, with sourcing:**

- *Examples that don't run*: this is widely reported anecdotally (developer blog posts, API-doc guides) but I did find one clean quantitative proxy: a 2026 study benchmarking LLM code generation against real API updates found that without comprehensive documentation, models averaged only 42.55% executable code, and even with structured documentation and larger models the executable rate topped out at 66.36% — a rough measure of how much "helpful-looking" example code in the wild simply doesn't run once an API has moved on.
- *Reference drifting from code*: covered concretely in the Rust community's own admission — a Rust core team member acknowledged there wasn't a strict culture requiring the reference manual be updated alongside every behavior change, though a bug-filing rule existed as a weaker substitute.
- *No version indicator*: raised explicitly as a positive differentiator for Django ("a version switcher... shows banners when reading docs for unreleased/insecure/old versions") and Elasticsearch ("the feature where you can switch ES version without leaving the page") — implying its *absence* is a recognized complaint elsewhere, though I don't have a survey quantifying how common the absence is.
- *Explanation buried inside instructions*: this is close to word-for-word the "tangled" smell in the Khan et al. benchmark above, and it's the smell most correlated with two other smells (bloated, excess structural info) in their data.

## 5. Configuration-heavy and agent/workflow tools

This is where the general advice needs the most adjustment for your case, because your closest comparables — linters, CI systems, build tools, and now AI agent frameworks — don't primarily produce prose that a human reads start to finish. They produce configuration surfaces that get referenced, and, increasingly, instruction files that get *parsed by a model* rather than read by a person.

**Linters and CI: reference has to be generated, not hand-maintained, or it silently rots.** ESLint's own documentation is structured as: getting-started guide → configuration guide (concepts) → auto-generated rules reference (one page per rule, generated from rule metadata) → extension/plugin guide. The rules reference is explicitly generator-produced — a dedicated tool, eslint-doc-generator, exists specifically to standardize and auto-update rule documentation across thousands of ESLint plugins, explicitly to "eliminate the custom documentation scripts... previously built and maintained by many ESLint plugins" and keep docs from drifting out of sync with rule metadata. GitHub Actions follows the same split at a larger scale: a dedicated "Reference" section (workflow syntax, events, expressions, contexts, variables, metadata syntax — twelve separate reference pages) kept structurally distinct from the how-to and conceptual guides, because a YAML schema this large can't be safely explained inline every time it's used.

**AI agent instruction files are a different genre entirely, and the evidence here directly bears on your product.** The emerging standard is AGENTS.md — described by its own maintainers as "a README for agents," now stewarded by the Agentic AI Foundation under the Linux Foundation — plus tool-specific variants (Cursor's `.cursor/rules/*.mdc`, CLAUDE.md). Two structural facts stand out:

- **Precedence, not prose, is the hard problem.** The closest AGENTS.md to the file being edited wins; explicit user chat prompts override everything. OpenAI's own Codex repository uses 88 separate AGENTS.md files across its directory tree rather than one global file — the documentation problem for this genre is less "what to say" and more "where does this rule live, and what beats what." Your equivalent decision (does a project-level rule override a global default? does a more specific config win?) is a documentation-architecture problem your closest comparables solve by explicit, written resolution order, not by narrative explanation.
- **More context is not better, and this is now measured, not assumed.** A rigorous February 2026 study out of ETH Zurich (Gloaguen et al., built on 138 real repositories specifically constructed to test this) found that providing context files does not generally improve task success rates, while increasing inference cost by over 20% on average — holding across different LLMs, coding agents, and both LLM-generated and developer-committed files. Instructions in context files are well followed, but repository overviews, although popular and recommended by model providers, are not helpful. Breaking that down further: LLM-generated context files reduced task success by an average of 3% versus no context file at all, while human-written files offered a marginal 4% average gain on the custom benchmark — at the cost of a similar 19% increase in inference steps. I cover why this matters to you in the contradictions section below — it's one of the strongest pieces of evidence in this whole research request.

**Net effect for your genre:** the traditional Diátaxis split (tutorial / how-to / reference / explanation) still applies to the *human-facing* docs about your tool — "how do I set this up," "why did we design rules this way" — but it does not apply to the config/rules files themselves, which are a fifth category the standard vocabulary doesn't cover: machine-parsed instruction text, where brevity and non-redundancy are empirically load-bearing, not just a style preference.

## 6. Staying current as it grows

**Docs required in the same PR** is the most commonly stated policy, but the practiced version is looser than the slogan. Kubernetes runs the most mature version of this at scale: every enhancement determined to need documentation must have its docs PR in a ready-to-merge state by the release's "Docs Freeze" deadline, or the enhancement is pulled from the milestone entirely (an exception has to be explicitly granted by the responsible SIG). That's real enforcement, but it's gated at the *release* level, not literally the same PR — feature code and docs are tracked as linked-but-separate deliverables, with a feature-tracking sheet listing each feature, whether it needs docs, and whether the docs PR has merged, reviewed weekly and colored green/yellow/red, and a named **Docs Lead** role responsible for chasing it down. Rust's own community explicitly *relaxed* a stricter version of this rule: a rule requiring reference-manual updates alongside behavior changes was "slightly relaxed" so that a bug must be filed rather than the literal text written immediately — an acknowledgment that blocking merges on finished prose doesn't survive contact with a fast-moving compiler team.

**Named owners** shows up as a recurring signal in how ADR/decision-log directories decay or don't: directories that name a specific person per decision (rather than "the team") tend to stay coherent, because a future reader has someone to ask; unowned records are the ones left "orphaned by authors who left two years ago," marked Accepted while the team quietly stopped following them. That's a practitioner pattern-observation from a documentation-tooling blog rather than a controlled study, so treat it as informed opinion, not measured fact — but it's consistent with the Kubernetes model above, where a specific Docs Lead (not "SIG-docs" abstractly) owns the freeze process.

**Periodic audits** are practiced, though evidence for their *effectiveness* specifically (versus other approaches) is thin. The clearest concrete example I found is procedural rather than survey-based: a UK government service's ADR carries an explicit review date field — "This page was last reviewed on 14 March 2024. It needs to be reviewed again on 14 June 2024" — with a note that a missed review "might mean the content is out of date." That's a real, functioning audit trigger, but I have no data comparing teams that do this against teams that don't.

**Generated reference** has the strongest direct evidence of preventing drift, because it removes the manual-sync step entirely rather than relying on discipline. Rust's doctest system extracts every code example from a doc comment and compiles and runs it as part of `cargo test` — if the underlying code changes and an example breaks, the build fails, catching the rot before a user hits it — which is a large part of why docs.rs was named repeatedly in the HN threads above specifically because the tooling makes docs "built-in" rather than a separate maintained artifact. It's not free, though: practitioners report the doctest infrastructure has real friction at scale (some larger projects reportedly adopt a "no doctests" policy), so the tradeoff is real engineering cost against drift prevention, not a pure win. The ESLint rules-reference generator and Kubernetes's generated API/kubectl reference are the same pattern applied to configuration surfaces rather than function signatures.

**What I can't tell you:** there's no controlled comparison of "PR-gated docs" vs. "named owners" vs. "periodic audits" vs. "generated reference" measuring which one actually reduces drift most, on comparable projects. Everything above is either a single case study or a practitioner's pattern-observation. Generated reference is the one mechanism with a plausible causal story for *why* it works (it removes the manual step rather than relying on someone remembering to take it) — the rest rely on process discipline, which is exactly the thing that tends to erode under deadline pressure.

## 7. Publishing reasoning

**ADRs (Architecture Decision Records)** are the most standardized format: title, status, context, decision, and consequences, following the structure Michael Nygard proposed in a 2011 blog post, now supported by tooling (adr-tools, MADR) and adopted across AWS, Microsoft Azure, Google Cloud, and most large engineering organizations. An academic comparison of ADR templates found real friction underneath the popularity: architectural rationale is rarely recorded in practice because of a genuine tension between documentation overhead and agile delivery pressure — teams prioritize simple, low-maintenance structures over complete ones, and there's essentially no rigorous comparison in the literature of which template structure actually works better. The same paper does cite one positive controlled comparison: a pre/post intervention study found that introducing ADRs significantly improved team satisfaction and reduced reliance on individual memory for knowledge transfer.

**Do people actually use them, or ignore them?** Mixed, and the honest answer depends heavily on maintenance discipline, not the format itself. On one hand, a case study that went back and actually reread a team's ADRs after the fact found only 1 of 8 ADRs contained information relevant to the process the team said it cared about — a signal that ADRs are easy to write and then not revisit. On the other, the failure pattern described by practitioners isn't "nobody reads them," it's "people read stale ones and act on outdated reasoning as current fact" — arguably worse than being ignored, because an ADR authored by people who've since left, describing a team structure that no longer exists, actively misleads rather than just sitting unused. I'll flag that source's own framing honestly: it describes itself as a composite of practitioner surveys and post-mortems, not a controlled study, so treat the mechanism as plausible rather than proven.

**RFCs** are the pre-decision counterpart — longer-form, open for input before a decision is reached, often converted into an ADR afterward to record the outcome — used at scale by Rust (public RFC repo with community comment periods), Kubernetes (KEPs), and internally at companies like Uber, where every project of non-trivial complexity required a brief design doc circulated to all engineers for comment.

**Practical takeaway for you:** the format (Nygard's five fields) is not the differentiator — nearly everyone uses roughly the same one. What separates directories people trust from directories people learn to ignore is (a) a named owner per record, and (b) mechanically-updated supersession links when a decision changes, not just a status field nobody revisits.

## Findings that cut against common advice

1. **"Give the agent more context" is measurably wrong for machine-facing docs.** The standard advice for any documentation is "more complete is better." For AI agent instruction files specifically, the opposite was measured: context files increased inference cost over 20% while not improving — and for LLM-generated files, actively reducing — task success rates. Since your tool *is* an agent-behavior configuration surface, this isn't a side note — it directly contradicts the intuition that thorough config documentation always helps the thing consuming it.

2. **Diátaxis has near-universal theoretical endorsement and almost no completed large-scale adoption to point to.** Every team I found that engaged with it seriously either partially absorbed the vocabulary, expanded it (GitHub's seven types), or stalled mid-audit (Python, three-plus years running). The common failure mode isn't "we tried it and reverted" — it's agreement followed by the restructuring simply never finishing, which is a different and less visible risk than the framework's advocates usually warn about.

3. **The most-repeated advice to separate content types by purpose is contradicted by the single most-praised documentation site in the survey data.** Django's defining, most-cited quality is the *opposite* of separation — deliberate layering where tutorial, concept, reference, and source are interlinked and each layer carries some of every type. The developers praising it specifically credit the connective tissue, not the separation.

4. **"Require docs in the same PR" gets weaker, not stronger, as projects scale.** The largest, most disciplined public example (Kubernetes) enforces at the release-freeze level with a named human role chasing it down — not literal same-PR blocking — and Rust explicitly softened a stricter rule because blocking merges on finished prose didn't survive contact with a fast-moving team. The practice that sounds most rigorous in theory becomes the most institutionally expensive to actually run.

## Five structural decisions for your documentation site, and the argument that decides each

**1. Split human-facing docs from agent-facing config files as two separate documentation problems, not one.** *Decider:* the Gloaguen study shows the two audiences respond to opposite treatment — humans benefit from more explanation and connective narrative (Django's model), while the config/rules files your agent actually parses measurably perform worse when padded with repo-overview-style content. Treating them as one "documentation" effort will optimize the wrong thing for one of the two readers.

**2. Use Diátaxis as a diagnostic vocabulary for reviewing pages, not as a mandatory folder structure you commit to building up front.** *Decider:* every team that tried to do the full upfront restructure (Python) stalled for years; every team that used it loosely as a lens (checking "is this how-to secretly explaining theory?") shipped. Commit to the cheap version of the practice that has evidence of finishing, not the expensive version that has evidence of stalling.

**3. Make your reference section generated from the config schema itself, not hand-written.** *Decider:* generated reference (Rust doctests, ESLint's rule-doc generator, Kubernetes's generated API/kubectl docs) is the only mechanism in this whole research pass with a causal story for preventing drift — it removes the manual sync step rather than depending on someone remembering to do it — and your tool, being config/rules-driven, has a schema to generate from.

**4. Write an explicit precedence/resolution-order page as its own top-level section, separate from your conceptual docs.** *Decider:* for every config-and-rules tool studied (AGENTS.md, Cursor rules, GitHub Actions contexts), the single highest-value piece of reference content wasn't "what each option means" but "what wins when two rules conflict" — and it's exactly the kind of content that gets buried inside how-to guides if you don't give it a dedicated home, which is precisely the "tangled" smell shown to correlate with the highest developer-reported productivity cost.

**5. Name a specific owner on every design-reasoning record (ADR/RFC), not a team.** *Decider:* the one variable that consistently distinguishes ADR directories people still trust from ones they've learned to ignore is whether a specific person, not "the team," is attached to each decision — it's the cheapest structural change available and it's the one with the most consistent (if not rigorously controlled) support across the sources.
