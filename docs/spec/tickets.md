# Tickets

How Flow holds a project's work. A ticket is one piece of work: its status, its plan and its history, in one folder. A project's tickets live in the Flow home, and `.flow/` in the project is a link to them, so every code branch sees the same tickets. The `flow` command creates, moves and ranks them. Typing `#exp` lists the open tickets, and a ticket the agent reads arrives with a header of its live fields.

## Scope

- **In**: the ticket's folder and fields, ids, where a project's tickets live, sync of tickets, the `flow` ticket and board commands, the `#` ticket list and the ticket header, the status moves the agent makes, and what a ticket records about its sessions.
- **Out**: `flow init` and the rest of setup, in `docs/spec/setup.md`. What `/flow:handoff` writes into a ticket, in `docs/spec/skills.md`.

## A ticket's life

Each status, and what moves a ticket into it:

```text
   todo           ready to work, nothing else
     │  flow tickets start: the agent, once it has read the ticket
     ▼
   in-progress    someone is on it, from the first question to the last check
     │  flow tickets done: the agent, once its own check passes
     ▼
   done           a dependent ticket unblocks here, and only here

   flow tickets start on a done ticket reopens it.
   parked (put off) and dropped (cancelled) sit beside the line, each with a reason.
```

## Behaviors

### The ticket

- `V1` **A ticket has a short `title` and a `description`.** The title is up to 4 hyphenated words, `login-redirect-loop`. The description is one sentence that opens with the short name and a colon: `Login redirect loop: the page reloads after a wrong password`. `flow tickets new` cuts the title from the words before the first colon, else the first 4 words. `flow tickets edit <id> --title` renames. Flow joins the id and the title as the ticket's name, `exp-47-login-redirect-loop`, in every list, message and badge. A title with capitals, spaces or over 40 characters is refused. Decided with the user 2026-10-14: a required `--title` made the agent write the same idea twice. Renames will be frequent, so the name leaves the folder (`fw-16` map `## 20.5.4`).
- `V1` **One folder per ticket**, `.flow/tickets/<id>/`: `ticket.md`, `context.md`, `history.md`, and what the work writes, such as `reports/`, `protos/<name>/` and `jobs/<job>.md`. A ticket made earlier still holds its `groundwork/map.md`, `plan.md` and `issues.md`, until `/flow:upkeep` reads them.
- `V1` **`ticket.md` says what the ticket is for and how you know it is done**, then `## Questions` if the work needs design and `## Tasks` if it needs building. Both lists are optional. `## Questions` nests as deep as the subject needs, and `flow tickets get <id>` counts every box at every indent (`scripts/features/tickets/store.ts`). `flow tickets get <id>` counts the boxes in each, `questions: 3/7 answered` and `tasks: 2/5 done`, and skips a box inside an HTML comment. `flow tickets new` writes no `map.md`, no `plan.md` and no `issues.md`.
- `V1` **A ticket holds its work in 2 files: `ticket.md`, the index, and `context.md`, the sections** (`fw-204`, the user 2026-10-24, built by `fw-267`). `flow tickets new` writes both, `context.md` holding only `## Loose`. `flow tickets get <id>` prints the index and a `context:` line naming the sections, `context: context.md 0, 0.1, Loose`. `ticket.md` holds current truth: what the ticket is for, the `## Questions` tree, each answered line with its one-line answer, each decision in short (what, a one-line why), `## Tasks` and `## References`. No line cap. `context.md` has one `##` section per question handle (`## 1.2`), edited in place: what was decided, found and rejected with reasons, and a pointer to the report holding the detail. A heading that fits no handle goes under `## Loose`, moved when its topic settles. Everything needed to continue after a restart, a clear or a handoff sits in the 2 files, written as each answer locks. Why: one piece of work sat in about 29 files, and decisions filed by subject did not suit groundwork, where many topics move at once.
  - `next` **One test sorts a line into the 2 files, in every phase: who needs it** (`fw-284`, the user 2026-10-25). `ticket.md` holds what anyone resuming needs before doing anything: what it is for, what is decided (short), what is open, the plan, a trap that would bite again. `context.md` holds what one question or task needs while it is worked: the why, the evidence, what was rejected, a dead end's story, implementation detail. Headings in `ticket.md` are optional, `## Decisions` included, for a decision with no question or task to hang on. The shape of both files lives in `guides/write-tickets.md`, sent on any touch of a ticket file (`docs/spec/rules.md` `### Guides sent by situation`). Groundwork, execute and handoff point to it, and it takes over `references/workflow.md`'s section list. Why: every rule by phase or by kind broke on a case, and the shape sat in 5 copies that disagreed. Refused: one build section in `context.md`, which grows into the journal refused below.
  - Refused: a journal appended in order and never rewritten (proposed 2026-10-24). A flat log reads as scratch, not context, and a restart would need a marker saying how far the index reflects it.
  - Refused: a line cap on `ticket.md`, 100 proposed.
  - `never` **Decisions moved to `decisions/<subject>.md` once they outgrew `ticket.md`**, past about 300 lines. Replaced 2026-10-24 by `context.md` (`fw-267`): a file per subject did not suit groundwork, where many topics move at once. An older ticket keeps its files, and `flow <id>` still lists them.
- `V1` **A section is written with `Edit` under its heading, and read alone**: `context.md#1.2` in the restart tool's `files`, or one `sed` from the heading to the next.
- `V1` **The agent keeps `## References` in every phase**, from pickup to done: the tools, files and folders the ticket needs, each with a short note where it matters. A restart or a new session starts from them.
- `V1` **One active ticket per session.** In a parent and child pair the child is active, and the parent's index is read for the decisions they share.
- `V1` **Big work is cut into children.** A child names its parent in `parent:`. The parent's `## Tasks` lists its children in build order, one line each that starts with the child's id: `- [ ] fw-127: …`. `flow tickets done` on a child ticks that line, and reopening the child clears it. A parent closes after its last child. `deps` stays for the rare wait outside the family.
- `V1` **Labels are tags**: `labels: [feature, v1]` in the frontmatter, several per ticket, each in lowercase letters, digits and hyphens, 24 characters at most. Flow works in full on a ticket with no label, and nothing in its code reads a label to decide what to do.
- `V1` **`activity:` is the kind of work under way on an in-progress ticket**, one word of 1 to 8 lowercase letters: `design`, `build` or `debug`. The word is open, and `refine` and `ideate` are `design`. `flow tickets start <id> --activity <word>` sets it at pickup, also on a ticket already in progress, so naming the work costs no extra call. `flow tickets edit <id> --activity <word>` changes it by hand, and an empty value clears it. Any status move clears it, and a ticket that is not in progress refuses it. Only `/flow:groundwork` (`design`), `/flow:execute` (`build`) and `/flow:debug` (`debug`) set it. No skill switches it mid-work: `proto` and `research` were dropped on 2026-10-18 because each switch and its reset cost 2 calls, for words that seldom apply. The agent may still set any word by hand. `flow tickets get <id>` prints an `activity:` line while one is set. The band (`fw-137`) shows it in capitals and reads it before any word derived from the ticket. Decided with the user 2026-10-18.
- `V1` **Flow suggests 9 labels**: `feature`, `bug`, `chore`, `docs`, `refactor`, `research`, `topic`, `new-project` and `urgent`. They are named in docs and skills only. No list sits in the code, and every label is free, such as `v1`, `post-v1` or `security`. `new-project` marks a whole project brainstormed from scratch. Not suggested, on purpose: `wontfix`, `duplicate`, `invalid` (that is `dropped` with a reason), `blocked` (that is `deps`), `question` (that is a `topic`), `idea` (a note holds a raw idea, and `parked` holds put-off work), `epic` (children already show a big parent), and `enhancement`, `help wanted`, `good first issue`.
- `V1` **`type` and `priority` are gone.** The kind of work is a label, and an urgent mark is the label `urgent`. Decided with the user 2026-10-11 and 2026-10-14: `type` was redundant, since a ticket's contents already say what kind of work it is.
- `V1` **5 statuses**: `todo` is ready to work and nothing else. `in-progress` is under way, and a ticket waiting on the user stays there. `done` is closed by the agent once its own check passes, and the user reopens it in a word. `parked` is put off, with a reason saying what brings it back. `dropped` is cancelled, with a reason. No project adds a status. One field says where the work is.
- `V1` **Only `done` satisfies a dependency.** A ticket still `in-progress` can change under the work built on top of it.
- `V1` **A new ticket always starts `todo`.**
- `V1` **One rule orders every ticket.** Tickets with the same parent are siblings, and top-level tickets share the empty parent. Among siblings, a ticket with `rank:` comes first, by number, and the tickets without one follow by id. A new ticket has no rank, so it lands last. A list across parents sorts level by level from the top parent down, so a child sits where its parent sits.
- `V1` **`flow tickets rank <id> --before <id>` (or `--after`, `--first`, `--last`) writes a number on the moved ticket alone.** The number is the middle of its new neighbours, after Backlog.md's `ordinal`. The first move in a group with unranked tickets numbers the whole group once (1000, 2000, …), then places the ticket. A gap too small to split numbers the group again. Decided with the user 2026-10-14. Refused: an order field beside priority, a list file holding the order, and `flow tickets move` as the command name.
- `V1` **Frontmatter changes only through `flow`.** A hand edit to the body rides along with the next commit.
- `V1` **No ticket for 3 kinds of work**: a small task asked in chat, a `/flow:research` question, and a subagent's job, which works under the ticket that sent it. Agreed by the user 2026-10-01: the board would fill with 2-minute tickets.

### Ids

- `V1` **An id is a short word and a number**: `exp-47`. The word is `ticketPrefix` in the project's `.flow/settings.json`, 2 to 8 lowercase letters, asked once by `flow init`. The pattern is Backlog.md's, Linear's and Jira's.
- `V1` **A ticket's files hold no prefix.** The folder is `.flow/tickets/<n>/`, and `id`, `parent` and `deps` are bare numbers, or `word-n` for a ticket of another project. The prefix lives in `ticketPrefix` alone, so changing it renames every id with no file touched. Prose that mentions an id (`fw-16` in a doc or a ticket body) stays as written. A parent's `## Tasks` line for a child is matched by the child's number and ignores the word, so a rename keeps its tick. Decided with the user 2026-10-19 (`fw-111` 1.2, built in `fw-208`).
- `V1` **A clashing prefix is one edit, with no rename command.** The first project registered keeps a prefix; a clone that claims the same one works inside its own folder, stays unregistered, and `flow doctor` names the clash and the setting to change. Changing `ticketPrefix` moves the project's registry line on its next ticket write, and the old prefix stops routing. `scripts/tests/projects.test.js` walks making, routing, listing and renaming a prefix across 2 projects and home.
- `V1` **Tickets outside any project use `home`**, live in `~/.flow/tickets/`, and their ids work from anywhere: `home-4`.
- `V1` **A project's id works from any folder, through the registry.** `locate()` reads the id's word: `home` goes home, the word of the project you stand in (or no word) is that project, and any other word is looked up in `registry.json`. The folder you stand in wins, so a clash never changes what a project sees of itself. An unknown prefix fails naming `flow doctor` and saying a project registers by its first ticket write. A registered folder with no `.flow/` or another `ticketPrefix` is refused with the cause. Decided with the user 2026-10-19 (`fw-111` 0.0, 2.0).
- `V1` **Outside a project a read shows the home place and a write refuses.** `flow tickets` and `flow next` show the tickets in `~/.flow/tickets`, under the header `home  ~/.flow`, and create nothing. `flow tickets new`, `flow notes new` and a status move on a bare number refuse, naming `flow init` here and `--project home`. An id that names its place (`home-4`, `bee-1`) needs no project, so it works and prints no header. Decided with the user 2026-10-19 (`fw-111` 2.1).
- `V1` **Every `flow tickets` and `flow next` list begins with one header line**: `fw  ~/code/flow-dev`, the prefix and the project's folder, with `~` for the home folder. It is the same inside a project, with `-p`, and in a folder that is no project (`home  ~/.flow`). It replaced `outside a project: showing ~/.flow/tickets`, which read as unclear. The user asked for one structure everywhere, 2026-10-20, and `fw-212` built it. `flow tickets get <id>` prints no header, since its id names the place.
- `V1` **`--project <prefix>`, short `-p`, reaches another project on `flow tickets new`, `flow tickets`, `flow next` and `flow notes new`.** One resolver, `projectNamed`, reads it: `home`, the prefix of the project you stand in, or a registered prefix. A command with an id reads the project from the id and takes no flag. `global`, `all` and a folder are refused, a folder with the prefix the registry holds for it. Short flags are a `short:` property of a value flag in `parseArgs`; `-p` is the only one so far (`fw-149` rule 6 assigns the rest). Decided with the user 2026-10-19 (`fw-111` 2.0, built in `fw-211`).
- `V1` **`home`, `global`, `all` and `here` are no prefix.** `flow init` refuses them and `offerWord` steps round them: a folder named `global` is offered `glo`, `home` is offered `hom`, `all` is offered `flow`. Merges `fw-163`.
- `V1` **A note names its project by prefix, `home` for the Flow home.** `project: shop` in its header, never the folder name, and `global` is gone. `--project` on a note needs a prefix registered on this machine, as a typo guard. A `project:` query term checks the prefix's shape alone, since notes travel between machines and the registry does not. Notes filed before this carried the folder name or `global`; `lab/scripts/convert-notes.js` rewrote them once on the main machine, and a note on another machine meets it by running the script there. There is no read-time shim for the old words.
- `V1` **A number is never given out twice in one place.** `ticket-counter`, beside `version`, holds the highest number the place ever gave out, committed with its tickets. The next number is the higher of the counter and the highest ticket, plus 1. Ruled with the user 2026-10-07: numbering from the tickets on disk freed the number of a ticket deleted, moved away or taken back, and `fw-16` went to a second ticket.
- `V1` **A bare number means the current place's ticket**: `12` inside the expense app is `exp-12`.
- `V1` **A typed name is read by its id alone.** `exp-47-old-words` finds `exp-47` after any rename. A title word that matches one ticket finds it too. A ticket made before the title moved out of the folder keeps its old folder name, and the same lookup finds it.
- `V1` **`flow tickets move <id> <home|prefix>` renumbers into the target**, and the ticket keeps `was: exp-12`, so the old id still finds it, from any project that routes the old prefix. The destination is a prefix looked up in the registry; a folder is refused with a message naming the prefix. A link to a ticket staying behind refuses the move.

### Where a project's tickets live

- `V1` **In the Flow home.** `.flow/` in the project is a link to `~/.flow/projects/<name>/`, made by `flow init` and hidden by `.git/info/exclude`, so the code's history never holds a ticket. `flow sync` carries the folder. The folder's `settings.json` holds the repository's address, so `flow init` in another clone finds it. Ruled 2026-09-29: a `.flow/` committed with the code gave each branch its own copy, so 2 branches invented one number, and a status moved on one branch stayed old on the other.
- `V1` **An older project keeps working.** A `.flow/` that is a checkout of the branch `flow`, or a plain folder, is still read. No command makes either, and `flow init` makes the link alone.
- `V1` **Tickets cannot conflict across code branches**, since every branch shares one checkout. 2 people conflict only on the same ticket, since each ticket is its own folder.
- `never` **A place on one machine alone**, built and removed 2026-10-01: the user ruled the case not worth a flag in V1.
- `never` **Flow's project rules kept in the Flow home, loaded through `CLAUDE.local.md`**: machinery for an isolation V1 does not need.

### Sync

- `V1` **Every command writing a ticket commits**, the whole folder, so the user's hand edits ride along.
- `V1` **A push follows a status move or a drop, in the background**, and after a reply once 30 minutes have passed with something changed, and at session end. The user asked for more than session end, and at most every half hour.
- `V1` **A findings or notes write starts no sync**: `flow findings new`, `flow findings edit`, `flow notes new`, `drop`, and `promote`'s note removal. They leave with the next 30-minute sync, at session end, or by `flow sync`. Ticket creation, status moves, drops, moves, `rank` and `init` still sync at once, since each sets a number or a claim the other machine must see early. Decided with the user 2026-10-27: 156 `flow findings edit` calls in a row started 156 syncs, which queued on the records lock until the next edit gave up after 20 seconds (`fw-312`).
- `V1` **One sync per place runs at a time.** A sync asked for while one runs leaves a mark, `~/.flow/records-sync.<place>.again`, and the running one goes once more when it ends. A write made during a sync still leaves at once, never at the next checkpoint. A runner's mark older than 5 minutes belongs to a run that died, and is taken over.
  - Refused: the network outside the records lock. A pull rewrites the working tree, and a write during it would be lost.
- `V1` **A pull runs at session start, in the background, and right before a new ticket takes its number.**
- `V1` **`flow tickets new` pushes at once, or makes no ticket.** Offline, no ticket is made, and git's own words are printed. A number shown and then changed would stay wrong in every plan, commit message and conversation that already used it. Decided with the user 2026-09-29.
- `V1` **2 machines taking one number: the later `flow tickets new` makes no ticket**, prints `no ticket was made: another machine took exp-5 first. Run it again.`, and leaves no trace. The retry takes the next number. Both folders are now `exp-5`, so the 2 tickets meet on the same file, and git cannot tell them apart or renumber one. A rebase replays every commit, so a ticket made and later removed would stop each later pull.
- `V1` **The Flow home claims a number the same way**, for a home ticket and a project's. `flow tickets new` runs `flow sync` on `~/.flow/` before taking the number. Then it commits every changed file there, merges, and pushes before the id shows. Offline, or on a clash in another file, no ticket is made. Decided with the user 2026-10-07: a number taken on the spot was renumbered at the next sync, mostly in the background, and the new id printed nowhere. Every changed file goes up, not the ticket alone, since git refuses to merge in the other machine's work over an uncommitted file it changed.
- `V1` **`flow sync` still renumbers a clash in the Flow home, keeping `was:`**, and prints `home-4 is now home-5: another machine took home-4 first.` Only a ticket made before claims existed, or while the Flow home had no remote, meets it. A Flow home with no remote numbers on the spot.
- `V1` **A pull meeting the same lines of one ticket changed on both sides is put back**, with the local version committed for a merge by hand.

### The board

- `V1` **`flow next` prints what to work on**: the in-progress work as a tree, then the ready list, then a `take:` line, then the parked count and what waits for `/flow:upkeep`.
- `never` **`flow tickets tree` shows a split feature whole**: every level, each parent's count of children done, and what blocks each ticket. Kept by the user 2026-10-01. Refused 2026-10-26 (`fw-234`): `flow tickets` draws the same tree by default, so a second command would be a second way to one job. The code and its tests are in `lab/archive/tickets-tree/`.
- `V1` **`flow next` and `flow tickets` print children under their parent, to any depth** (`fw-234`, decided by the user 2026-10-20, renamed by `fw-149` 2026-10-26). Each row carries its count of children done, `26/35` (done of total), the same short form as the band, what blocks it, and the first words of a parked reason. `--flat` gives the plain table. Everything `tree` did has a counterpart in `flow tickets -- "<query>"`: `--all` is `status:all`, `--parent <id>` is `parent:<id>`. Siblings and roots order by status, started before new, then by rank. The command layout sits in `docs/spec/product.md`, section "The flow command".
  - **A ticket whose parent the query filtered out is rooted, its row saying `under fw-16`.** Why: it keeps what the flat table's `PARENT` column told. Refused: the missing parent as a dim context line, since `flow` has no colour yet.
- `V1` **`flow next` shows in-progress work as a tree** (`fw-149`, the user 2026-10-26, drawn in `.flow/tickets/archive/149/next-output.md` version 2). Every in-progress ticket appears, a parent with its done count and every open child under it, with no cap. Among siblings, an in-progress child sorts before todo ones, then rank. A line holds one colon at most: with nothing ready it prints `nothing ready. 2 todo tickets blocked`. Why: the flat list hid `fw-16`, `fw-172` and `fw-204`, named no parent, and padded with less important work.
  - Refused: 3 todo children per parent then `and N more`. A few lines cost few tokens.
  - Refused: an issues count line, and leaving `flow-issue` tickets out of the ready list by a rule. Issues are tickets, harvested in their own sessions, and a parked group (`fw-235`) sets them aside. The session start view already counts labels.
  - `later` A per-project setting for what `flow next` shows.
- `V1` **The text and the JSON of `flow next` differ** (the user 2026-10-26): the JSON serves the board and holds the whole ready list; the text serves the user and the agent, and cuts it to 3 rows. Both come from one view, `graph.nextView`, computed once.
- `V1` **A ticket list's JSON is flat, in display order, one record per ticket with `parent` and `depth`** (`fw-234`). One record shape (`scripts/features/tickets/json.ts`) serves every list and every write, and `flow tickets get` adds the body, children and dependents. `flow tickets --json` is the forest order with `--flat` too, so `depth` means one thing in every run. Why: the mod and the hooks read the commands, so the nesting rules stay once, in `scripts/`. `--json` on every command is in `docs/spec/product.md`, section "The flow command".
- `V1` **A label with a card is a group** (`fw-235`, decided by the user 2026-10-21, built 2026-10-27). The card is `.flow/groups/<label>.md` with `title`, `rank`, `parked:` (the reason, once) and optionally `group_by: label`; membership is carrying the label. `flow-issue` is a group built into the code, with no file. Groups are made on purpose, never automatically, and do not nest. They have their own noun (`fw-149`, 2026-10-26), since a group is never started: `flow groups` lists, `flow groups rank <label> --first|--last|--before <label>|--after <label>` ranks, `flow groups park <label> --reason "<why>"` and `flow groups revive <label>`. A rank or a park makes the card, and a label no ticket carries is refused with the labels in use. Refused: a labels file, a field on the ticket, parent tickets as groups (`v1` and `post-v1` cut across parents, and `seo` gets new tickets after it looks finished).
  - **`flow groups rank` takes relative moves, like `flow tickets rank`** (the user 2026-10-27). Why: with `--rank N` the user picks numbers and tracks the gaps. A group is ranked among the ranked groups alone, so the first move ranks no other card.
  - **Only a ranked group reorders a list.** `flow next` and `flow tickets` print each ranked group's tickets under its label, in rank order, before the rest. A ticket sits once, under the first ranked group among its top ancestor's labels, so a child stays where its parent sits. Why: a section for every unranked group would sink `flow-issue` tickets below the rest by a rule, which `fw-149` refused.
  - **Any parked group holds a ticket, whatever its other labels.** The file keeps its stored `status`; `store.statusOf` reads a held ticket as `parked`, so it is never ready, never in the in-progress tree, and its `--json` record says `status: parked` with `heldBy`, and `storedStatus` the file's own. `flow tickets get` prints `status: todo (held by post-v1)`, and `flow next` prints `15 held by post-v1` beside the parked count. `flow tickets start` refuses a held ticket unless `--force`, naming `flow groups revive`. Why: a started ticket that `flow next` hides would be work nobody sees.
- `V1` **`flow tickets check` finds cycles, dangling ids, dropped blockers, orphaned parents, unknown statuses, and a ticket with no title or description.**
- `V1` **A one-time script converts the old tickets**, `lab/scripts/convert-tickets.ts`, never a `flow` command, archived to `lab/archive/` after its real run. It rewrites only the frontmatter of each `ticket.md`: the old `title` becomes the `description`, the new `title` is the folder's words, `type` becomes a label, the old statuses become `in-progress`, and `priority` goes. A live `priority: high` ticket takes a `rank` among its siblings, so it keeps its place ahead of the unranked ones. Every other priority just goes. Maps, plans, reports, prototypes and folder names are not touched, and a second run changes nothing. Decided with the user 2026-10-14: a harvest into new tickets would break every id and link, for what a frontmatter rewrite does at no loss. A script, since no one but the user holds old-shape tickets.
- `V1` **`flow tickets -- "<query>"` takes one quoted query**, the grammar `flow notes` reads (`scripts/shared/query.ts`). Fields: `label`, `status`, `parent` (the ticket and its whole subtree, counted the same by `flow tickets labels`), `filed` (`filed:no` is a closed ticket `/flow:upkeep` has not filed) and words. A comma inside a value means either, a repeated field means both: `"label:flow-issue label:rework-loop"`. Rank order. The flags `--status`, `--label`, `--parent` and `--unfiled` are gone, with no migration. Decided with the user 2026-10-19: one grammar for notes and tickets, and drilling down is label intersection, so no label has to sit in one place of a tree.
- `V1` **`flow tickets` hides parked, done and dropped tickets unless the query names a `status:` term.** `status:all` shows every status, as `project:all` does in notes, and the count line says how many are hidden. `flow next` keeps its `--all` flag. Decided with the user 2026-10-19.
- `V1` **`flow next` is small: name per ticket, labels in the ready list, parked as a count, and a `take:` line.** Every session opens on it and pays for each line in context. Decided with the user 2026-10-19, reshaped by `fw-149` 2026-10-26.
  - **The ready list holds every ready ticket outside the tree**, children of todo parents included, in rank order, `flow-issue` ones too. The text shows 3, then `and 52 more (flow next --all)`. `--limit` is gone. Why: a child of a todo parent would show nowhere else. Refused: leaving `flow-issue` tickets out by a rule, since a parked group (`fw-235`) sets them aside.
  - **`take:` is the first ready ticket in the tree, from the top, else the ready list's first.** Never a blocked todo, which `flow tickets start` would refuse.

## One real case: working a ticket

1. The user types `/flow:execute `, then `#exp-47`, and takes the row. The prompt reads `/flow:execute @.flow/tickets/47/ticket.md`. The skill loads, Claude Code attaches `ticket.md`, and the mention hook adds the header.
2. `/flow:execute` reads the ticket, then runs `flow tickets start exp-47`. `history.md` gains a line with the session id, and `branch: feature/budgets` is recorded. The move commits and pushes in the background.
3. The user approves the plan, and the agent builds it with the ticket still `in-progress`. Each task ticks in `## Tasks`, and a trap hit gets its section in `context.md`.
4. The context fills, and the agent restarts the window.
5. The restarted window starts from `ticket.md` and the `context.md` sections the note names. Its `Read` of `ticket.md` gets the header again, since the new window holds none.
6. The tests pass. `flow tickets done exp-47` unblocks `exp-48`, which depended on it, and `flow next` ranks `exp-48` first.

## How it fails

- **Offline, `flow tickets new`** → no ticket, and git's words printed.
- **2 people take one number at once** → the later `flow tickets new` makes no ticket, leaves no trace, and says to run it again.
- **2 machines take one `home-` number at once** → the later `flow tickets new` merges, finds the clash, makes no ticket, and says to run it again.
- **A home ticket made before claims existed clashes** → `flow sync` renumbers it, with `was:`.
- **The same ticket changed on both sides** → the pull is put back, the local version stays committed, and the user merges by hand.
- **A typed `exp-99` for no such ticket** → plain text reaches the phase, and the agent finds no ticket.
- **`flow` fails, times out or knows no such ticket on a `Read`** → the read passes with no header, and the mod logs the cause.
- **A ticket path under `~/.flow/projects/<name>/tickets/`**, the folder `.flow/` links to → no header, since no project root sits in the path.
- **`.flow/` deleted by hand** → the next `flow init` links it again. The tickets sit in the Flow home and are untouched.

## What is locked

- **Tickets live in the Flow home, not with the code.** One folder for every code branch is what makes ids and statuses agree across branches.
  - Refused: a branch of the project's repository (`lab/archive/branch-storage/`). Its one gain was that a teammate who could read the project could read its tickets, and Flow is a personal workflow.
  - The risk named: Beads ran a sync branch and deleted it, 5,720 lines of repair, because every issue sat in one file. One folder per ticket is the answer.
- **An id carries its place's word**, so 2 places never produce one id. A letter per place, `g4`, was refused: `t` reads as ticket and `g` does not.
- **One way to name a ticket to a skill: an `@` mention of its `ticket.md`, written by a `#` list row** (`fw-236`, the user 2026-10-21). The row shows the title and status, which a typed id cannot, and the mention brings the header with it.
  - Refused: one skill per ticket (approved 2026-09-30, archived 2026-10-27). The folders went stale between commands, and the agent's own `Read` of a ticket got nothing.
  - Refused: 20 declared arguments so a short instruction expands to nothing. Nobody reading the skill would understand it, and it rests on behavior the docs never promise.
